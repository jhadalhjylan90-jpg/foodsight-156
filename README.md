# FoodSight

تطبيق عربي مستقل لإدارة مخزون المطاعم، متابعة الهدر، والتنبؤ بالطلب. الكود HTML / CSS / JavaScript مع خادم Node.js محلي، وقاعدة PostgreSQL فعلية في Supabase. لا يستخدم Sites ولا يحتاج تثبيت حزم npm.

## التشغيل على Windows

1. ثبّت Node.js 22.9 أو أحدث (يفضل Node.js 24 LTS).
2. فك ضغط المشروع بالكامل.
3. افتح `start-windows.bat`.
4. افتح `http://localhost:3000` في المتصفح.
5. أول مرة فقط: ستظهر شاشة ربط قاعدة البيانات. افتح رابط مفاتيح مشروع Supabase الموجود فيها، وانسخ **Secret key** أو **service_role** والصقه ثم اضغط **حفظ الاتصال وفتح التطبيق**.

بعد هذه الخطوة يفتح التطبيق مباشرة كل مرة، **بدون تسجيل دخول أو حساب أو كلمة مرور**. المفتاح يحفظ في `.env` على جهازك، ولا تحتاج تعديل أي كود. لا ترسل المفتاح في المحادثة ولا تشارك ملف `.env`.

من الطرفية على Windows أو macOS أو Linux:

```sh
cd foodsight
npm start
```

أبقِ النافذة مفتوحة أثناء استخدام البرنامج. يتطلب الإنترنت للوصول إلى Supabase. الخادم يستمع على `127.0.0.1` فقط، فلا ينشر التطبيق على الشبكة. يمكن تغيير PORT في ملف `.env` عند الحاجة (من `.env.example`). 

## الموجود فعليًا في قاعدة البيانات

- مشروع: `ksemtrbeouvagobyrbvi`.
- 17 جدولًا، وعرض يجمع المبيعات التاريخية ومبيعات POS الجديدة.
- 3 فروع: بريدة، عنيزة، الرس.
- 5 وجبات: برجر لحم، برجر دجاج، شاورما دجاج، بطاطس، سلطة.
- 11 مكونًا ووصفات بالكميات والوحدات الأساسية.
- 365 يومًا، من 2025-09-30 إلى 2026-09-29؛ 5,475 سجل مبيعات يومية تجريبية.
- 12,078 دفعة تاريخية وحالية و36,168 حركة مخزون وقت التأسيس؛ الأعداد تزيد مع الاستخدام.
- البيانات كلها مولّدة للمشروع. التاريخ مخزن كملخصات يومية لا كفواتير POS حقيقية، مع زيادة مفترضة في نهاية الأسبوع ويوليو وأغسطس وأواخر الشهر، وحالات نفاد مسجلة.

الجداول والبيانات منفذة بالفعل. **لا تعِد تنفيذ ملفات الإنشاء أو التعبئة على المشروع الحالي.** مجلد `database` يوثق المصدر لإعادة البناء في مشروع جديد فارغ، بترتيب الملفات المرقمة. `verify.sql` اختبارات تتراجع عن تغييراتها في النهاية. تاريخ بداية التعبئة نسبي إلى تاريخ تشغيل ملف البذور، لذلك إعادة إنشائها مستقبلًا تنتج سنة مختلفة.

## استخدام التطبيق

- **نظرة عامة:** ملخص المبيعات والهدر، منحنى المبيعات وتنبيهات الصلاحية.
- **أداء الفروع:** حدد الفرع والفترة واليوم لرؤية الوجبات واستهلاك الوصفات.
- **المخزون والدفعات:** تسجيل استلام بالغرام/الكيلو أو الملليلتر/اللتر أو الحبة/العبوة، مع الصلاحية؛ نقل بين الفروع؛ جرد وهدر وسجل حركات.
- **تعبئة حسب الوجبات:** اختر 30 برجر مثلًا؛ يحسب المكونات، ثم يطلب صلاحية كل منها قبل تسجيل استلامها جميعًا في معاملة واحدة. لا يعتبر ذلك بيعًا أو مخزون وجبات جاهزة.
- **التنبؤ والتخطيط:** 7 أو 14 أو 28 يومًا، مع هامش احتياط قابل للتعديل، وشراء مقترح حسب العبوة، ومواعيد نقص متوقعة، وتوريدات منتظرة، وخطة تحضير قابلة للتعديل والحفظ.
- **جرّب POS:** اختر الفرع والوجبات ثم أتم الطلب. تخصم قاعدة البيانات الوصفة من دفعات الفرع الأقرب انتهاءً. الطلب غير الكافي يُرفض كاملًا، وإعادة الطلب بالمفتاح نفسه لا تخصم مرتين.

## الحسابات والافتراضات

- الرصيد ينشأ من سجل الحركات؛ Trigger يحدّث رصيد الدفعة في المعاملة نفسها. يوجد قيد يمنع الرصيد السالب.
- الشراء أو خطة التحضير لا يغيران المخزون حتى يتم الاستلام أو البيع/الهدر فعليًا.
- مكونات كل بيع مرتبطة بنسخة الوصفة. واجهة الوصفات الحالية للعرض؛ تعديل نسخ الوصفات يتم من قاعدة البيانات.
- التنبؤ متوسط مرجح لأيام الأسبوع المماثلة خلال السنة الماضية، مع وزن أعلى للأسابيع الثمانية الأخيرة وللشهر وفترة الشهر المماثلة. تستبعد الأيام المسجلة بنفاد مخزون. ليس تعلمًا آليًا معقدًا ولا يتضمن ضمان دقة أو اختبار دقة تاريخيًا بعد.
- نطاق التوقع وصفي، مبني على الانحراف المعياري، وليس فاصل ثقة معايرًا.
- المخزون المناسب يحاكي الاستهلاك اليومي لكل فرع على حدة، ويخصم ما بيع اليوم من الكمية المخطط لها. يقيّم صلاحية الدفعات عند منتصف اليوم؛ لا يحاكي ساعات الخدمة.
- صلاحية التوريدات المنتظرة افتراضية حسب المكون حتى تسجل الصلاحية الفعلية عند الاستلام. توصية الشراء إجمالي عجز الفترة، وليست أمرًا باستلام كل شيء يومًا واحدًا. المواد سريعة التلف تحتاج توريدات موزعة.
- انتهاء الصلاحية يمنع بيع الدفعة، لكنه لا يسجل هدرًا تلقائيًا. سجّل الإتلاف الفعلي لتظهر تكلفته ضمن الهدر.
- مدد صلاحية بيانات العرض افتراضية، **ليست تعليمات لسلامة أو حفظ الغذاء**. الاستلام الفعلي يطلب تاريخ صلاحية يدويًا.
- سجل الحركات في الواجهة يعرض آخر 400 حركة في الفترة؛ القاعدة تحتفظ بكل التاريخ.

## الاتصال المحلي بدون تسجيل دخول

لا توجد شاشة تسجيل دخول ولا حسابات داخل التطبيق. الخادم المحلي يحتفظ بمفتاح الاتصال في `.env`، ولا يرسله إلى ملفات الواجهة أو المتصفح عند الاستخدام. شاشة الربط الأولى ترسل المفتاح إلى الخادم على جهازك فقط، ويتحقق من الاتصال قبل حفظه. ملف التحميل لا يحتوي مفتاحًا سريًا جاهزًا.

قاعدة البيانات غير مفتوحة للعامة: RLS مفعّل، وأدوار anon وauthenticated بلا صلاحية للجداول والدوال. يستخدم الخادم المحلي مفتاح server-side. لا تشارك ملف `.env` أو تنشر هذا الخادم على الإنترنت؛ تصميمه للاستخدام على جهازك فقط. يبقى ملف `config.json` محتويًا رابط المشروع دون أي مفتاح.

## الملفات

- `server.mjs`: خادم محلي واتصال REST بقاعدة البيانات، مع إعداد الاتصال مرة واحدة.
- `app.js`: شاشات التطبيق والتفاعلات.
- `logic.js`: تحويل الوصفات ومحاكاة الاحتياج حسب الدفعات والصلاحية.
- `styles.css`: الهوية والاستجابة للجوال؛ #FFB36B و#28323C.
- `assets/`: خطا IBM Plex Sans Arabic الأصليان وشعارا FoodSight الأصليان.
- `database/`: إنشاء الجداول والدوال والبذور وحماية الوصول المحلي والاختبارات.
- `tests/`: اختبارات حساب احتياجات الوصفات والمخزون والتواريخ.

```sh
npm test
```

## التحقق

نجحت اختبارات قاعدة البيانات للخصم الدقيق، وعزل الفرع، ومنع تكرار الخصم، والتراجع الكامل عند العجز، وتحويل كجم إلى غرام، والهدر، والجرد، والنقل مع حفظ الصلاحية، وسلامة الرصيد مقابل سجل الحركات. الدخول العام للجداول والدوال محجوب؛ التطبيق يتصل عبر الخادم المحلي فقط.

اختبارات تفاعلات الواجهة تستخدم لقطة فعلية مقروءة من قاعدة Supabase مع اعتراض اتصال الاختبار فقط؛ التطبيق الموزع لا يحتوي بيانات واجهة ثابتة ولا وضع بيانات وهمي محلي. إدخال مفتاح الاتصال المحلي خطوة عند أول تشغيل. لم أختبر اتصال الخادم بهذا المفتاح الخاص بالمستخدم لعدم توفره؛ تم اختبار العمليات مباشرة على قاعدة Supabase واختبار تفاعلات الواجهة بصورة منفصلة. تعذر تشغيل متصفح للفحص البصري في بيئة التنفيذ بسبب قيود تشغيل المتصفح؛ لا يُدّعى اكتمال فحص بصري على جهاز المستخدم.
